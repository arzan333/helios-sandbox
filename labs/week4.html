Helios Week 4 lab book Training environment

Two Documents a Model Can Read

Self-paced. Follow along on your own machine, or watch and run it afterwards. Every command has a copy button.

Time 40 minutes You produce two specifications converted, repaired and given an owner, a small repository with index files and a CLAUDE.md, and one question answered twice and scored Committed locally, never pushed Needs Claude Code 2.1.211 or later, Python 3.11, pandoc, markitdown with its PDF extra, this repository
The job. You are given two specifications for an order service: a functional one in Word and a technical one in PDF. Neither can be searched, quoted or pointed at. In forty minutes you turn them into markdown with real headings, intact tables and an owner on every file, put a folder and a CLAUDE.md around them, and measure what that was worth.

The catch. Both conversions succeed, and both drop facts that are written down nowhere else. Step 2 is one command that proves it in thirty seconds.

The shape of the session

StepWhat you doTime
1Convert both documents, and count what came out0-8
2One command showing what the conversion dropped8-13
3Repair the headings and the tables13-22
4Build the folder, and write the CLAUDE.md22-32
5One question, asked twice, scored both ways32-40
Three prompt patterns, and every prompt below is labelled with one in the grey bar above its copy button.
  • analysis reads something and reports. The output is a finding, so it always has to name its evidence.
  • coding transforms files. The output is a diff, so it is always followed by a command that checks it.
  • validation checks a claim somebody has already made. The output is a score or a verdict, and it never writes the thing it is checking.
Labelling costs no time at all. It is worth doing because a prompt that converts a file and tells you the conversion went well has marked its own homework.
0Set up before the clock starts

Why. Today needs two converters the other weeks never used, and a check now is cheaper than a confusing error in six minutes.

a. Check your tools. In a plain PowerShell window:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
claude --version
python --version
python -c "import importlib.util as u, shutil; print(shutil.which('pandoc') or 'pandoc MISSING'); print('markitdown can read PDF' if all(u.find_spec(m) for m in ('markitdown','pdfminer','pdfplumber')) else 'markitdown PDF SUPPORT MISSING')"
Expected. Two version lines, a path, and a sentence:
output - the versions and the pandoc path are yours
2.1.260 (Claude Code)
Python 3.11.9
C:\Users\you\AppData\Local\Pandoc\pandoc.EXE
markitdown can read PDF
Claude Code must be 2.1.211 or higher and Python 3.11 or higher. Your pandoc path will not match this one; what matters is that it is a path rather than MISSING.

The last line asks whether markitdown can read a PDF, not whether it is installed. Those are different questions: markitdown keeps its format support in optional extras, so the check imports all three pieces by name. If either the path or the sentence comes back wrong, the first two rows of the table at the end of this book have the one command that fixes it.

b. Pull in this week's files and make your folders. Safe to run twice:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
git fetch origin
git merge origin/main -m "Week 4 files"
mkdir week4 -Force | Out-Null
mkdir week4\raw -Force | Out-Null
dir docs\specs\ordercore-fsd.docx
dir docs\specs\ordercore-techspec.pdf
dir templates\frontmatter-schema.md
Expected. A merge summary, then the three names below. PowerShell heads each listing with its folder and a Mode, LastWriteTime, Length and Name table, and it puts files from the same folder under one heading, so three dir lines arrive as two tables. The names are the part that matters; the dates and sizes are yours:
output - names only, sizes and dates vary
ordercore-fsd.docx
ordercore-techspec.pdf
frontmatter-schema.md
cannot find path on any of the three means the merge brought nothing. Read the git message above the error, and tell your facilitator - the week's files may not have been published yet.

One dir per line, on purpose. dir a b c is not valid PowerShell: the second path is taken as a filter and the third has nowhere to go, so you get either a wrong answer or A positional parameter cannot be found. Every listing in this book is one path at a time for that reason.

c. Start Claude Code. This is the only thing you need to launch:

powershell

You now need two windows. The one you just typed claude in is Claude Code, and every block labelled prompt below is pasted into it. Open a second PowerShell window for every block labelled powershell - from the Start menu, or inside VS Code with Ctrl+Shift+`. 1Convert both documents 0-8 min

Why. Word and PDF need two different converters, and neither of them tells you what it could not carry.

a. One prompt runs both converters. It is a coding prompt: it transforms files and nothing else.

prompt - coding 
Convert two specifications to markdown. Run both of these from the repository
root, exactly as written:

    pandoc docs/specs/ordercore-fsd.docx -t gfm -o week4/raw/fsd.md
    python -m markitdown docs/specs/ordercore-techspec.pdf -o week4/raw/techspec.md

Then write week4/conversion-log.md: the two commands, which converter read
which format, and the exit code each returned.

Convert nothing else, and change nothing inside either output file - they are
the raw conversions and a later step measures them. Reply with one line: the
two exit codes.
Expected. Two commands run, a short log written, and one line back:
output
pandoc 0, markitdown 0
Both converters are silent when they succeed, so the exit codes are all you get. Say Yes to the two commands and to the log; there is nothing else for this prompt to touch.

b. Now measure what arrived, rather than trusting that it arrived:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\raw
python -c "import re,pathlib; [print(p.name, len(re.findall('(?m)^#', t)), 'headings,', len(re.findall('(?m)^[|][-| :]+[|]', t)), 'table separators') for p in sorted(pathlib.Path('week4/raw').glob('*.md')) for t in [p.read_text(encoding='utf-8')]]"
Expected. A listing of the two conversions, then two measured lines:
output - the two counts are exact on every machine
fsd.md 0 headings, 6 table separators
techspec.md 0 headings, 9 table separators
Zero headings in both is the finding, not a failure. Both conversions succeeded. Neither produced a single markdown heading, because in the Word file the headings were styled by hand and in the PDF they are text that happens to be bigger than the text around it. What made those documents navigable was a visual convention, and visual conventions do not convert.

Six is right and nine is wrong. The functional specification has six tables and all six came through. The technical specification has four, so nine separator rows means the converter started a fresh table every time a row wrapped onto two lines in the PDF. Step 3 puts those back; carry both numbers until then.
2What the conversion dropped 8-13 min

Why. A converter that exits zero has told you that it finished, and nothing at all about what it could not carry.

a. Five facts, one command. Each of the five lives in a diagram in the PDF:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
python -c "import pathlib; t=pathlib.Path('week4/raw/techspec.md').read_text(encoding='utf-8').lower(); [print(('present' if w in t else 'ABSENT '), w) for w in ['8080','no retry','404','820','p50']]"
Expected. Five lines, all the same:
output - exact, on every machine
ABSENT  8080
ABSENT  no retry
ABSENT  404
ABSENT  820
ABSENT  p50
Those five strings are the port the service listens on, the rule about retrying a failed call, the status code for an order that does not exist, a measured response time, and the label on every median in the performance chart. The conversion carried every word of prose in that document and not one of these, because each of them was drawn rather than written.

One of the five is worth a sentence on its own: a chart held a measurement, and the measurement is gone. The prose still says a limit is being breached; the number that proved it does not survive, so nothing in the converted document connects the claim to its evidence.

Thirty seconds, and it is repeatable. That matters more than it sounds: the same command run after the next conversion tells you whether the same five facts are still missing, which a paragraph written about this conversion never could. A present on any line means the file came from something other than the conversion in step 1; delete it and send the step 1a prompt again.
3Repair the headings and the tables 13-22 min

Why. A heading is the only thing a retrieval tool can aim at, and a broken table is worse than a missing one because it still looks converted.

a. One coding prompt does both files. Read its last paragraph before you send it:

prompt - coding 
Rewrite week4/raw/fsd.md as week4/repo/specs/ordercore-fsd.md and
week4/raw/techspec.md as week4/repo/specs/ordercore-techspec.md.

Headings. Give every section the level its own numbering implies. The document
title is level 1. A whole-number section, and an appendix, is level 2. A
two-part number like 1.1 is level 3, and a three-part number like 4.1.1 is
level 4. The numbering is written inconsistently in the originals: make the
heading text consistent, and change no section number.

Tables. week4/raw/fsd.md has six tables and they all arrived intact, so carry
them across untouched. week4/raw/techspec.md has four tables and the PDF
conversion broke all four: some rows came through as markdown rows and some as
plain prose directly above or below them, and some tables were cut in half by
a second separator row. Rebuild each of the four as one header row, one
separator row, and every data row as a markdown row, in the order they already
appear. Where a row wrapped onto two lines, join it.

Take every word from those two files. Do not open the .docx or the .pdf, and
do not add a row, a column or a cell that is not already in the text. One
table in the technical specification exists only as an image, so its contents
are not in the file at all: leave a line saying so where it belongs, and
reconstruct nothing.

Change no wording outside a heading line. Reply with one line: how many data
rows each of the four repaired tables ended up with.
Expected. Two files written, and four counts:
output
6, 5, 3, 5
Six field mappings, five configuration settings, three test suites, five known gaps: nineteen rows. A higher count is an invented row, and the usual invention is a sixth known gap. Ask Claude to quote the line each row came from and the invented one will have no quotation.

The table that does not come back is the point of the last paragraph. One table in that document was pasted in as a picture, so no converter and no prompt can recover it - the words were never in the file. An answer that quietly produces a plausible table in its place is the worst outcome of this step, because it is exactly as convincing as the four real ones.

b. Count what came out. The separator numbers are the ones to read:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\repo\specs
python -c "import re,pathlib; [print(p.name, len(re.findall('(?m)^## ', t)), 'level-2,', len(re.findall('(?m)^[|][-| :]+[|]', t)), 'separators,', len(re.findall('(?m)^[|]', t)) - 2*len(re.findall('(?m)^[|][-| :]+[|]', t)), 'data rows') for p in sorted(pathlib.Path('week4/repo/specs').glob('*.md')) for t in [p.read_text(encoding='utf-8')]]"
Expected. A listing of two files, then two measured lines:
output - the level-2 count on the first line may read 15
ordercore-fsd.md 16 level-2, 6 separators, 37 data rows
ordercore-techspec.md 7 level-2, 4 separators, 19 data rows
Read the second line first. Four separators where step 1 counted nine, and nineteen data rows: the four tables are whole again. Five separators means one is still cut in half. Twenty or more data rows means a prose line that was never part of a table got promoted into one.

On the first line, six separators and thirty-seven data rows must not have moved - those are the same six tables, carried across untouched. The level-2 count reads 15 or 16 depending on whether the document control block at the front was treated as a section, and both are right. Twenty means subsections were promoted and the file is now flat.
4Build the folder, write the CLAUDE.md 22-32 min

Why. Retrieval is a folder problem before it is a model problem, and an unowned document does not go stale so much as quietly become wrong.

a. Front matter and index files, in one coding prompt:

prompt - coding 
Work only inside week4/repo.

1. Put a front matter block at the very top of
   week4/repo/specs/ordercore-fsd.md and
   week4/repo/specs/ordercore-techspec.md, in the exact shape and field order
   of templates/frontmatter-schema.md. Nothing goes above the block, not even
   a heading. Take owner, version, effective_date and review_date from the row
   for the original document in docs/governance-log.md, and invent no date.
   Add source: naming the original file it was converted from, and status:
   draft.

2. Write week4/repo/specs/index.md: one row per specification - file, what it
   covers in one clause, owner, review date.

3. Write week4/repo/index.md: one row per folder and per loose file directly
   under week4/repo - what is in it, and which index to read next. Pointers
   only, and no summaries of any document.

4. Give both index files front matter of their own, same schema. They were
   written today, so there is no row to copy: owner is Architect, version 1.0,
   effective_date is today, and review_date is six months after today.

Do not edit docs/governance-log.md, and do not edit anything under docs/specs.
Reply with one line: the two review dates you copied, and whether each one is
in the past.
Expected. Two files given front matter, two indexes written, one line back:
output
2026-07-12 past, 2026-09-03 past
Both dates are behind us, and that is the data telling the truth: the two documents that describe the service are the two nobody has re-read. If Claude produced today's date, or a date six months out, for either specification, it invented them - the prompt says where they come from and the two rows are four lines long. Send it again.

b. Now the file that is re-read on every single request. It is a coding prompt with a hard ceiling in it:

prompt - coding 
Read templates/claude-md-template.md and write week4/repo/CLAUDE.md for the
repository in week4/repo. Use the five headings the template gives and no
others.

- What is here: the two converted specifications and the two indexes. Two or
  three lines.
- Standards: the rules that would otherwise be repeated in every request about
  these documents. Front matter is mandatory and is the first thing in the
  file. Dates are ISO. A converted document keeps a source field naming its
  original. Money is a whole number of pence. Five or six lines at most.
- Where to look: point at week4/repo/index.md and week4/repo/specs/index.md,
  and say what each one answers. Point, do not summarise.
- Do not: week4/raw holds the raw conversions and is not the repository; the
  originals under docs/specs are never edited; a fact that was only ever in a
  diagram is not in this markdown and must not be filled in from memory.
- Ownership: one line, by role.

Under 400 words, which is about a page. Nothing a reader could get by opening
the directory. Reply with one line: the word count.
Expected. A short file, and a number under 400:
output - yours will differ
214 words
Anything between about 150 and 400 is a reasonable answer. Under 100 means a heading was left empty. Over 400 means a document got summarised inside the file instead of pointed at, which is the one mistake this file cannot afford: every word in it is paid for on every request, so its length is a running cost rather than a one-off.

c. Check all of it in one go:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\repo
python -c "import datetime,pathlib; g=lambda t,f: next((l.split(':',1)[1].strip() for l in t.splitlines() if l.startswith(f)), 'MISSING'); today=datetime.date.today().isoformat(); [print(t[:3], g(t,'owner'), g(t,'review_date'), 'past' if g(t,'review_date') < today else 'current', p.as_posix()) for p in sorted(pathlib.Path('week4/repo').rglob('*.md'), key=lambda q: q.as_posix()) if p.name != 'CLAUDE.md' for t in [p.read_text(encoding='utf-8')]]"
python -c "import pathlib; t=pathlib.Path('week4/repo/CLAUDE.md').read_text(encoding='utf-8'); print(len(t.split()), 'words'); [print(('yes' if h in t else 'NO '), h) for h in ['## What is here','## Standards','## Where to look','## Do not','## Ownership']]"
Expected. A listing, four front matter lines, then a word count and five headings:
output - the two 2027 dates are six months from the day you run this
--- Architect 2027-03-18 current week4/repo/index.md
--- Architect 2027-03-18 current week4/repo/specs/index.md
--- Product Manager 2026-07-12 past week4/repo/specs/ordercore-fsd.md
--- Architect 2026-09-03 past week4/repo/specs/ordercore-techspec.md
214 words
yes ## What is here
yes ## Standards
yes ## Where to look
yes ## Do not
yes ## Ownership
Every one of those four lines has to start with ---. Anything else means the block is not the first thing in the file, usually because a title was left above it, and a tool that reads front matter reads the first three characters and stops.

Two past and two current is the whole of the governance lesson. Nothing new happened to those two specifications this morning. A date that had already gone by is now in a field a command can read, instead of being invisible in a document nobody re-opens. That is all a review date does, and it is enough to make a stale document announce itself.

Two decisions the book made for you. The folder is organised by kind of document - specs/ - rather than by the system each document describes, because a document that covers two systems has nowhere to live in a by-system folder and both of today's do. The two new index files were given the Architect as owner and six months as a review interval, because an index that points at two specifications can be wrong for a while before anybody is hurt, and a short interval on a file that rarely changes only trains people to ignore the date.
5One question, asked twice 32-40 min

Why. Everything so far is a claim that the repository is better, and this is the only part of the session that could come out against you.

a. Ask the raw conversions. This is an analysis prompt: it reads and reports, and it writes no specification:

prompt - analysis 
Read only week4/raw/fsd.md and week4/raw/techspec.md. Use nothing else in this
repository, and nothing you already know about order services.

Answer this in week4/answer-raw.md:

  When a call from the order service to the billing service fails, how many
  times is it attempted, and what does the caller get back? Name the document
  and the heading each fact came from, and give the owner and the review date
  of each document you used.

If a fact is not in what you read, say so in those words and say where it
would have to come from. Fill no gap from memory. Under 200 words. Reply with
one line: how many of the four things asked for you could answer.
Expected. A short answer that mostly cannot answer:
output - one either way is fine
1 of 4
There are no headings to name, the retry rule went into a diagram, and neither raw file carries an owner or a review date in any field a tool could read. The one it can answer is what the caller gets back.

A confident four out of four is the answer to worry about. It means the run answered from what it knows about services in general rather than from the two files, and the retry sentence it produced will be plausible and unsourced.

b. Same question, same pattern, different sources:

prompt - analysis 
Read only what is under week4/repo. Start at week4/repo/index.md and follow
its pointers. Use nothing else in this repository, and nothing you already
know about order services.

Answer this in week4/answer-repo.md:

  When a call from the order service to the billing service fails, how many
  times is it attempted, and what does the caller get back? Name the document
  and the heading each fact came from, and give the owner and the review date
  of each document you used.

If a fact is not in what you read, say so in those words and say where it
would have to come from. Fill no gap from memory. Under 200 words. Reply with
one line: how many of the four things asked for you could answer.
Expected. Three, and the interesting part is which one is still missing:
output - 3 is the usual answer
3 of 4
The heading is nameable, the owner and the review date come out of the front matter you added in step 4, and the retry count is still not there - but now the answer says so in those words.

That is the win, and it is smaller and better than the one you were expecting. The repository did not recover a fact that was drawn rather than written. It made the absence visible, which is the difference between a document that is incomplete and a document that is misleading.

c. Score both. This is a validation prompt: it checks two claims and writes neither of them:

prompt - validation 
Score week4/answer-raw.md and then week4/answer-repo.md against these five
rows, 0, 1 or 2 each, out of 10. Score only what is written in the file, and
give no credit for what it probably meant.

1. Answers the question, or says plainly that these files cannot.
2. Names the document and the heading each fact came from.
3. Gives the owner and the review date of each document used.
4. Invents nothing - every sentence traceable to something it read.
5. Says where a fact it could not find would have to come from.

For every row, quote the words you scored, taken from the file. Where you
cannot quote anything, the row is 0.

Write week4/score.md: the two scored tables, the two totals, and a section
"## What the repository bought" of at most four lines saying which rows moved
and which did not. Change neither answer file.

Reply with one line: the two totals.
Expected. Two totals, a couple of points apart:
output - raw of 7 or 8 is the normal spread
raw 8/10, repo 10/10
The gap is smaller than you were expecting, and it is in rows 2 and 3. Rows 1, 4 and 5 come out the same in both, and usually high: both prompts told the run to say plainly when it could not answer and to say where a missing fact would have to come from, and a run that follows that instruction scores well whatever it is reading.

Row 2 moves because there is now a heading to cite instead of a file name, and row 3 moves because an owner and a review date are now fields instead of a sentence in a preamble. Those are steps 3 and 4, which is as direct a measurement of the session as you will get - and it says the repository bought an address and a provenance, not a better answer.

Equal totals mean the scorer credited a file name as a heading in row 2. There are no headings in week4 aw sd.md at all; step 1b counted them and the answer was zero. Point that out and ask it to score that row again.

d. Commit the lot as one thing:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\score.md
git add week4
git commit -m "Week 4 lab: two specifications turned into a repository"
git log --oneline -1
Expected. One listing, then one commit:
output - the hash and the branch name are yours
score.md
[main 4a91c23] Week 4 lab: two specifications turned into a repository
4a91c23 Week 4 lab: two specifications turned into a repository
Git lists every file it added between those two lines; the commit line and the log line are the two to read. The raw conversions go in as well as the repository, because six months from now the only way to tell whether a sentence is the author's or a converter's is to have kept both. Nothing is pushed; a hook blocks it.

Passing bar

Both documents converted, with the raw conversions kept. The five-string check run, and five ABSENT lines seen. Two specifications with a heading hierarchy: the functional one still showing six separators and thirty-seven data rows, the technical one showing four separators and nineteen data rows, and a line in it where the image-only table used to be. Front matter first thing in every file under week4\repo, with the two copied review dates reading past. Two index files that point and do not summarise, and a CLAUDE.md under 400 words using the template's five headings.
