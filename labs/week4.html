Helios Week 4 lab book Training environment

From Word and PDF to a Retrievable Repository

Self-paced. Follow along on your own machine, or watch and run it afterwards. Every command has a copy button.

Time 45 minutes You produce two specifications converted and given headings, a gap register with a verdict you typed in every row, a small repository with front matter and index files, a CLAUDE.md under a page, and one question answered twice and scored Committed locally, never pushed Needs Claude Code 2.1.211 or later, Python 3.11, pandoc, markitdown with its PDF extra, VS Code, this repository
The job. Everything anybody knows about OrderCore is in two files: docs/specs/ordercore-fsd.docx, a Word functional specification, and docs/specs/ordercore-techspec.pdf, a PDF technical specification. Neither can be searched, quoted, diffed or pointed at. In 45 minutes you turn them into markdown that a person or a model can retrieve one section of, and put a folder structure and a CLAUDE.md around them.

The question. A converter that exits without an error has told you nothing about what it dropped. Both of today's conversions succeed. Both lose facts that are written down nowhere else in Helios. The work is finding out which, and writing that down where the next reader will see it.

The shape of the hour

StepWhat you doTime
1Convert both documents, and look at what came out0-8
2Repair the heading hierarchy, carry every table across8-16
3Find what the conversion lost, and decide what it costs16-26
4Choose the folder shape, then build it with front matter and indexes26-34
5A CLAUDE.md under one page34-39
6One question, answered twice, scored both ways39-45

Step 3 is the one that matters. Steps 1 and 2 are mechanical - they are prompts, and they take eight minutes each because you are reading the result, not typing it. Step 3 is ten minutes of your own judgement, and nothing in it can be handed to a model.

Three prompt patterns, and every prompt in this book is labelled with one. Look at the grey bar above each copy block.
  • analysis - read something and tell me what is in it. The output is a finding. It can be wrong in a way that looks right, so it always has to name its evidence.
  • coding - transform files. The output is a diff. Success is checkable by running something afterwards, which is why a coding prompt in this book is always followed by a command.
  • validation - check a claim somebody has already made. The output is a pass or a fail. It never writes the thing it is checking.
Mixing them is the usual way a prompt goes wrong: a prompt that converts a file and tells you the conversion went well has marked its own homework.
0Set up before the clock starts

Why. This week needs two converters the other weeks never used, and a check now is cheaper than a confusing error in six minutes.

a. Check your tools. In a plain PowerShell window:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
claude --version

python -c "import importlib.util as u, shutil; print(shutil.which('pandoc') or 'pandoc MISSING'); print('markitdown can read PDF' if all(u.find_spec(m) for m in ('markitdown','pdfminer','pdfplumber')) else 'markitdown PDF SUPPORT MISSING')"
Expected. Two version lines, a path, and a sentence:
output - the versions and the pandoc path are yours
2.1.260 (Claude Code)
Python 3.11.9
C:\Users\you\AppData\Local\Pandoc\pandoc.EXE
markitdown can read PDF
Claude Code must be 2.1.211 or higher and Python 3.11 or higher. The pandoc path will not match this one; what matters is that it is a path rather than MISSING.

The last line is the one worth understanding. It does not ask whether markitdown is installed - it asks whether markitdown can read a PDF, which is a different question. markitdown keeps its format support in optional extras, and pip install markitdown installs the tool without any of them. Reading a PDF needs markitdown[pdf], which brings pdfminer.six and pdfplumber with it. The check imports all three by name for that reason; a version check on markitdown alone would pass on a machine where step 1a cannot run.
Only if that last line said MISSING

One command, once per machine, and it needs the internet. Then run step 0a again and expect markitdown can read PDF:

python -c "import importlib.util as u; print('markitdown can read PDF' if all(u.find_spec(m) for m in ('markitdown','pdfminer','pdfplumber')) else 'still MISSING')"

If pandoc said MISSING instead, open a new terminal first - an installer only adds itself to the PATH of windows opened afterwards. If it is genuinely absent, re-run setup/Setup-HeliosWorkstation.ps1, which installs pandoc through winget.

1Convert both, and look at what came out 0-8 min

Why. Two file formats need two different converters, and neither of them will tell you what it could not carry. Running them takes a minute. The seven minutes after that are you reading the result.

a. The PDF first, with your own hands, so you see a conversion arrive unfiltered:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
if (-not (Test-Path week4\raw\techspec.md)) { python -m markitdown docs\specs\ordercore-techspec.pdf -o week4\raw\techspec.md }
dir week4\raw\techspec.md
type week4\raw\techspec.md
Expected. Nothing from the conversion itself - markitdown is silent when it succeeds - then a listing, then about seventy-five lines of markdown. This is the part to read, the field mapping table from section 2.1:
output - week4/raw/techspec.md, section 2.1 exactly as it arrives
2.1 Field mapping
| OrderCore | Billing | Type   | Notes                 |
| --------- | ------- | ------ | --------------------- |
| order_id  | orderId | string | Echoed back unchanged |
unit_price_pence unitPricePence integer Whole pence, never a decimal
discount_percent discountPercent integer 0 to 50 inclusive, added HEL-207
| subtotal_pence | subtotalPence | integer | Derived, not stored |
| -------------- | ------------- | ------- | ------------------- |
tax_pence taxPence integer 20 percent, calculated once on the order
total_pence totalPence integer subtotal minus discount, plus tax
Look at what that is. One table has become a header, a separator, one real row, two rows of plain prose, a second real row, another separator where no separator belongs, and two more rows of prose. Every word survived. The structure did not, and the structure was the only thing that made it a table.

The column padding is markitdown's and may shift with its version. The shape - real rows, prose rows, and a separator row where no separator belongs - is what you are looking for, and it is the same on every machine.

The file is written only if it is not already there. Run the block twice and the second run changes nothing, which is what the Test-Path guard is for. Delete the file if you want the conversion again.

b. Now the Word file. This one is a prompt, because it is mechanical work with a command in the middle of it:

prompt - coding 
Convert the Word functional specification, and record what the conversion did.

Run this, from the repository root:

    pandoc docs/specs/ordercore-fsd.docx -t gfm -o week4/raw/fsd.md

Then write week4/raw/conversion-log.md:
- The two commands that produced week4/raw/fsd.md and week4/raw/techspec.md.
  For the pandoc one, the exit code you saw. For the markitdown one, write
  "run in the terminal in step 1a; printed nothing, which is how markitdown
  reports success" - you did not run it, so do not record an exit code for it.
- For each of those two files: how many markdown headings it contains (lines
  beginning with a hash), and how many table separator rows (lines beginning
  with a pipe and containing only dashes, spaces, colons and pipes).
- One line saying which converter reads Word on this workstation and which
  reads PDF, and what happens if you use the other one.

Convert nothing else and edit nothing else. Reply with one line: the heading
count in each of the two files.
Expected. Claude runs the command, writes the log, and answers:
output
fsd.md 0 headings, techspec.md 0 headings
Zero and zero is the finding, not a failure. Both conversions succeeded. Neither produced a single markdown heading, because the Word file styles its headings by hand instead of using heading styles, and a PDF has no headings at all - only text that happens to be larger than the text around it. Everything that made those documents navigable was a visual convention, and visual conventions do not convert.

The separator counts in the log are 6 for fsd.md and 9 for techspec.md. Six is right: the functional specification has six tables and pandoc carried all six. Nine is wrong, because the technical specification has four - and you have just seen why a broken table grows extra separator rows. Keep both numbers; step 2 checks them again.
Do not point markitdown at the .docx. It recognises the file and then stops with MissingDependencyException, because the Week 1 setup installs markitdown without its optional Word support. Pandoc reads Word and cannot read PDF; markitdown reads PDF and, here, cannot read Word. That is the whole of the tool choice, and it is worth a line in the conversion log so the next person does not spend ten minutes on it.
Rather run the pandoc command yourself?

Nothing is lost either way - it is the same command, and part b hands it to Claude only because the log has to be written in the same turn. If you would rather watch it run:

powershell - alternative to the prompt in part b 
cd $env:USERPROFILE\Helios\helios-sandbox
pandoc docs\specs\ordercore-fsd.docx -t gfm -o week4\raw\fsd.md
dir week4\raw\fsd.md

Pandoc is silent on success. Send the part b prompt afterwards anyway, so the log exists - step 6 scores what is written down, not what you remember doing.

2Repair the heading hierarchy 8-16 min

Why. A heading is the only thing a retrieval tool can aim at. Without one, a question about tax has to be answered by reading five thousand words, which is what you are paying to avoid.

a. One prompt does both files. Read what it is forbidden to do:

prompt - coding 
Read week4/raw/fsd.md and week4/raw/techspec.md and rewrite them as structured
markdown.

Write week4/repo/specs/ordercore-fsd.md and
week4/repo/specs/ordercore-techspec.md.

- Give every section the heading level its own numbering implies. The document
  title is level 1. "1. Introduction", "2 Background", "SECTION 3 - SYSTEM
  CONTEXT", "Appendix A" and "Appendix B" are all level 2. "1.1", "5.2" and
  "7.5" are level 3, and a three-part number like "4.1.1" is level 4. The
  numbering style is inconsistent in the original: make the style consistent in
  the heading text, and change no section number.
- Carry every table across exactly as it is. Do NOT repair the broken ones in
  techspec.md today. Leave them wrong, so the next step can count them.
- Change no wording anywhere outside a heading line. Do not summarise, do not
  reorder, and do not drop the figure captions.

You are moving furniture, not writing. Reply with one line: the number of
level-2 headings in each file.
Expected. Two files written, then one line:
output - one either way on the first number is fine
ordercore-fsd.md 16, ordercore-techspec.md 7
Seven is exact: the technical specification has sections 1 to 7. Sixteen depends on whether "Document control" was counted as a section alongside 1 to 13 and the two appendices, so fifteen or sixteen are both right. Twenty means subsections were promoted, and the file is now flat.

b. Check it rather than believe it. The same measurement as the conversion log, run by you:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\repo\specs
python -c "import re,pathlib; [print(p.name, len(re.findall('(?m)^## ', t)), 'level-2', len(re.findall('(?m)^[|][-| :]+[|]', t)), 'separator rows') for p in sorted(pathlib.Path('week4/repo/specs').glob('*.md')) for t in [p.read_text(encoding='utf-8')]]"
Expected. A listing of two files, then two measured lines:
output - the first number may read 15
ordercore-fsd.md 16 level-2 6 separator rows
ordercore-techspec.md 7 level-2 9 separator rows
The separator counts must not have moved. Six and nine are the numbers the conversion log recorded before any rewriting. If ordercore-fsd.md now reads five, a table was dropped. If ordercore-techspec.md reads four, the broken tables were quietly repaired - which is this week's hands-on and not this step; send part a again with the "leave them wrong" sentence emphasised.

Nine separator rows for four tables is the number to carry into step 3. A table that arrives in pieces is worse than a table that arrives as prose, because it looks converted.
This step wrote no front matter and no index. That is deliberate. Structure first, ownership in step 4 - a document nobody has read yet is not one you can honestly put a review date on.
3What the conversion lost 16-26 min

Why. Both conversions exited cleanly and both dropped facts written down nowhere else in Helios. If you do not record what is missing, the repository becomes confidently incomplete, which is worse than the Word file was.

a. Ask only what the converted text can support. The first paragraph is the whole of the method:

prompt - analysis 
Work only from week4/raw/fsd.md and week4/raw/techspec.md. Do not open the
.docx or the .pdf. Do not use anything you know about OrderCore from the code
or from anywhere else in this repository. You are standing in for a retrieval
tool that has nothing but this markdown.

Write week4/repo/gaps.md.

- A table, one row per figure caption in either file. Columns: Figure |
  Document | What the caption or the text around it says the figure holds | Is
  that fact anywhere in the converted text | Verdict.
- Column four is a quotation or it is "not in the text". Where it is a
  quotation, give the sentence. Where it is not, say which words you searched
  for.
- Put VERDICT-TO-DECIDE in every row of the Verdict column. That column is
  mine.
- Then a section "## What a reader cannot do": one line per question about
  OrderCore that these two files can no longer answer, each naming the figure
  the answer went into.

Supply no fact from memory. If a caption says something is recorded nowhere
else, that is a gap to report and not a hole to fill. Reply with one line: how
many captions you found, and how many of them hold a fact that is not in the
text.
Expected. A register written, and a count:
output - the second number is the one that matters
8 captions, 5 hold a fact that is not in the text
Eight is exact: four figures in each document. Five is the interesting number, and four or six is defensible - the argument is over the three Shop screens in the functional specification, whose content the text does describe elsewhere. The five that are not arguable:
FigureWhat went with it
Technical spec, Figure 1The port each service listens on. Nothing in either converted file names a port except the Billing base URL in the configuration table
Technical spec, Figure 2Whether a failed Billing call is retried, and how many times
Technical spec, Figure 3What each error condition logs, and the table that put condition, status, body and log level in one place. The functional specification does give the status codes in prose in 8.2, so it is the log levels and the single view that are gone
Technical spec, Figure 4Ten measured response times, including the one the document's own gap register calls a breach
Functional spec, Appendix BThe 2026 bank holiday dates the delivery window calculation depends on
Be precise about rows one and three, because a grep will be. Those two figures illustrate things the other document does describe: the fallback rule is in functional spec 3.2, 6.2 and NFR-4, and the error status codes are in 8.2. A gap register that claims more than that is wrong, and it is wrong in the direction that costs you credibility. What is genuinely nowhere is the log level for each condition, the ports, the retry count, the ten measurements and the bank holiday dates.

The functional specification is the more honest of the two: its own open item OI-3 says the bank holidays are an image and need to become data. The technical specification says nothing of the kind. Its captions claim the opposite - that these facts are recorded there and nowhere else - which turns out to be very nearly true.

Very nearly, and the exception is worth ten seconds. Figure 1's caption claims the ports, the Billing timeout and the fallback rule are recorded there and nowhere else - but section 5 of the same document lists the Billing timeout as 2000 ms in its configuration table, and gap TG-4 in section 7 says runtime orders are lost on restart. A caption is a claim like any other. If your register repeated that claim without checking it, correct the row: it is the ports and the fallback rule that are gone, not the timeout.

b. Do not take that on trust either. Six seconds, and it is the proof the whole lab rests on:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
python -c "import pathlib; t=pathlib.Path('week4/raw/techspec.md').read_text(encoding='utf-8').lower(); [print(('present' if w in t else 'ABSENT '), w) for w in ['no retry','8080','404','820','p50']]"
Expected. Five lines, all the same:
output - exact, on every machine
ABSENT  no retry
ABSENT  8080
ABSENT  404
ABSENT  820
ABSENT  p50
Those five strings are the retry rule, the port OrderCore listens on, the status code for a missing order, the measured p95 that breaches a requirement, and the label on every median in the performance figure. Not one of them survives into the converted text. The word "fallback" does survive, twice - once in a caption describing a picture you cannot see, and once inside the broken testing table, where it is the tail of a row that arrived as prose. Neither hit is the rule. That is the most dangerous of the three outcomes, because a search returns something.

A present on any line means your week4\raw\techspec.md came from something other than markitdown on this PDF. Delete it and run step 1a again.

c. Now look at the four pictures yourself. It is the only way to see them, and it takes two minutes:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir docs\specs\ordercore-techspec.pdf
Start-Process docs\specs\ordercore-techspec.pdf
dir week4\repo\gaps.md
code week4\repo\gaps.md
Expected. Two listings and a tab in VS Code, and in between them the PDF opens in whatever this machine uses for PDFs, which on the standard build is Edge. Opening the reader prints nothing:
output - names only, sizes and dates vary
ordercore-techspec.pdf
gaps.md
Pages 1 to 4, one figure each. Read Figure 4 on page 4 against NFR-2 in section 10 of the functional specification, which you now have as markdown and can search. The specification requires the invoice call to return within 800 ms. The figure measures it at 820 ms at p95. That is gap TG-3 in section 7 of the technical specification, which says a breach exists and never says by how much.

That is what an image-only fact costs. The number that proves the breach is in a picture; the claim that there is a breach is in text; and nothing in the converted repository connects them. Nobody did anything wrong. The document was written to be read by a person holding both files open.

If nothing opens, skip it - a PDF reader is not part of the workstation build, and the figures are described well enough above to finish the step.
Now the decision, and it is the only one in this lab. The tab you just opened is week4\repo\gaps.md. Replace every VERDICT-TO-DECIDE with one word: blocking if a reader would make a wrong decision without that fact, recoverable if somebody could go and get it inside an hour, cosmetic if nothing depends on it. At least one must be blocking, and you should be able to say in a sentence what would go wrong. Most people make Figure 3 blocking, because a team that cannot read the error contract writes a client that treats a fallback invoice as a failure.

Nobody can make that call for you, which is exactly why it is the part you type. Everything else in this step was a prompt.
4The folder shape, then build it 26-34 min

Why. Retrieval is a folder problem before it is a model problem. A structure chosen on purpose is the difference between pointing at one file and pasting a whole specification into every request.

a. Two shapes, and you pick one. Thirty seconds, but make the choice rather than inherit it:

shape a - by document type
week4/repo/
  index.md
  CLAUDE.md
  gaps.md
  specs/      index.md, ordercore-fsd.md, ordercore-techspec.md
  process/    not today - the narratives are already markdown
  rubrics/    not today - the gates are already markdown
shape b - by system
week4/repo/
  index.md
  CLAUDE.md
  gaps.md
  ordercore/  index.md, fsd.md, techspec.md, process.md
  billing/    index.md
  shop/       index.md

Only the first three lines get built today, and only specs/ of the folders - the process narratives and the rubrics are already markdown with front matter, so they need converting no more than they need moving. They are in the picture because a folder shape has to survive the documents you have not converted yet, and that is the thing you are choosing between.

Shape a survives a reorganisation of the estate, and it puts every document of a kind together, which is how documents are reviewed and how they go stale. Shape b is the shape a question arrives in - somebody asks about OrderCore, not about specifications - and it falls apart the moment a document covers two systems, which both of today's do. This book uses shape a for that reason. Choose shape b if you prefer; everything below names week4/repo/specs/, so that is the one path you would change as you go.

b. Build it, and give the two specifications an owner:

prompt - coding 
Build the repository around the two converted specifications. Work only inside
week4.

Add a front matter block to the very top of week4/repo/specs/ordercore-fsd.md
and week4/repo/specs/ordercore-techspec.md, in the exact shape and field order
of templates/frontmatter-schema.md. Take owner, version, effective_date and
review_date from the row for the original document in docs/governance-log.md.
Do not invent a date. Add source: naming the original file it was converted
from, and status: draft, because both originals are drafts.

Then write two index files.

week4/repo/specs/index.md - one row per specification: file, what it covers in
one clause, owner, review date, and whether that review date is in the past
today.

week4/repo/index.md - one row per folder and per loose file in the repository:
what is in it, and which index to read next. Pointers only. No contents, no
summaries of documents, nothing that has to be rewritten when a document
changes.

week4/repo/gaps.md already exists and has my verdicts in it. Give it a row in
the root index, and leave the file itself exactly as it is.

Reply with one line: the two review dates, and whether each is in the past.
Expected. Two files given front matter, two indexes written, and one line:
output
2026-07-12 past, 2026-09-03 past
Both dates come from docs/governance-log.md and both are behind us. That is not an accident in the data: the two documents that describe the service are the two nobody has reviewed. If Claude wrote today's date, or a date six months out, it invented them - the prompt says where they come from and the two rows are four lines long. Send it again.

c. Look at what you built:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\repo
type week4\repo\index.md
python -c "import pathlib; [print(p.as_posix(), repr(p.read_text(encoding='utf-8')[:3])) for p in sorted(pathlib.Path('week4/repo/specs').glob('*.md'))]"
Expected. A listing, the root index, then lines proving the front matter is the first thing in each file:

Anything other than '---' on the two specification lines means the block is not at the top - usually a title was left above it - and the schema is explicit that nothing goes above it, not even a heading. A tool that reads front matter reads the first three characters and stops.

index.md shows '---' only if Claude gave it front matter of its own. Either is fine today; the hands-on requires it of every file.
5A CLAUDE.md under one page 34-39 min

Why. This file is re-read on every single request in the repository, so every word in it is paid for every time. It is the one document where length is a running cost rather than a one-off.

a. Write it from the template, not from imagination:

prompt - coding 
Read templates/claude-md-template.md and write week4/repo/CLAUDE.md for the
repository in week4/repo.

Use the five headings the template gives and no others. Replace the guidance
under each with the real thing:

- What is here: the two converted specifications and the gap register. Two or
  three lines.
- Standards: the rules that would otherwise be repeated in every request about
  these documents. Front matter is mandatory and is the first thing in the
  file. Dates are ISO. Money is whole pence. A converted document keeps a
  source field naming its original. Five or six lines at most.
- Where to look: point at week4/repo/index.md, week4/repo/specs/index.md and
  week4/repo/gaps.md, and say what each one answers. Point, do not summarise.
- Do not: the raw conversions under week4/raw are working files and are not
  the repository; the originals under docs/specs are never edited; the content

Under 400 words, which is one page. Nothing that a reader could get by opening
the directory. Reply with one line: the word count.
Expected. A short file, and a number under 400:
output - yours will differ
212 words
Anything between about 150 and 400 is a reasonable answer. Under 100 means a heading was left empty. Over 400 means a document got summarised inside the index instead of pointed at, which is the failure the template warns about.

A NO is usually a heading renamed to read better. Put it back: a fixed set of headings is what lets somebody skim four of these files in a minute.

Read the Where to look section against the Do not section. If anything under Where to look would still be useful sitting in its own file with a pointer from here, it belongs in its own file. That is the template's own test, and it is the only thing that keeps this file small over a year.
6One question, answered twice 39-45 min

Why. Everything so far is a claim that the repository is better. This is the measurement, and it is the only part of today that could come out against you.

a. Ask the raw conversions first:

prompt - analysis 
Read only week4/raw/fsd.md and week4/raw/techspec.md. Use nothing else in this
repository, and nothing you already know about OrderCore.

Answer this in week4/answer-raw.md:

  When the call from OrderCore to Billing fails, how many times is it
  attempted, and what does the caller get back? Name the document and the
  heading each fact came from, and give the owner and the review date of that
  document.

If a fact is not in what you read, say so in those words and say where it
would have to come from. Do not fill a gap from memory. Under 200 words.
Reply with one line: how many of the four things asked for you could answer.
Expected. A short answer that mostly cannot answer:
output - one either way
1 of 4
