Helios Week 3 lab book Training environment

Ship a Small Change, Then Gate It

Self-paced. Follow along on your own machine, or watch and run it afterwards. Every command has a copy button.

Time 45 minutes You produce an impact note, one change across Python and Java, a gate rubric of your own, and a score you gave yourself Committed locally, never pushed Needs Claude Code 2.1.211 or later, Python 3.11, a JDK, VS Code, this repository
The job. HEL-207 adds an optional discount to an order. Sales agree a percentage with a wholesale customer, OrderCore carries it, and Billing takes it off the subtotal before tax. Six acceptance criteria, already written. It is a small change - and it crosses the one place in Helios where Python calls Java.

The question. Nobody is going to review this today. So how do you know it is finished? By the end you will have a gate you wrote yourself, a score you gave yourself against it, and a rework you did because the score said so.

The shape of the hour

StepWhat you doTime
1Plan before you generate - an impact note from the entity map, checked against the code0-7
2Pick the model tier, and name what no model gets a vote in7-12
3The Python side, in one small diff12-22
4The Java side, so the contract is whole22-30
5Run the two gates that are not opinions30-34
6Adapt the design rubric into your gate, and score yourself with it34-42
7Rework what failed, then one commit42-45

Three of those seven steps happen before any code is written, and one of them is you reading the code rather than the map. That ratio is the lesson. The eighteen minutes in steps 3 and 4 are mostly spent reading two diffs; the generating itself is the short part.

Why this ticket, of all the tickets

It crosses a language boundary. OrderCore names its fields in snake_case, Billing in camelCase, and the translation lives in one file. Change one side only and nothing throws.

It has a fallback that hides the failure. When Billing cannot be reached, OrderCore works the invoice out locally and marks it. A half-changed contract therefore looks like a working invoice with the wrong total on it.

It is small enough to finish. Four files in Python, three in Java. If a gate cannot be run on a change this size, it will never be run on a big one.

2Pick the tier, and name what no model decides 7-12 min

Why. The model you reach for out of habit is a cost decision you never made, and some of the work in this lab should not go to a model at all.

Three tiers, priced in data/model-pricing.csv as at 1 September 2026:

TierModelInput, per millionOutput, per millionWhat it is for
fastHaiku 4.5$1.00$5.00Classification, extraction, routing. High volume, low judgement
balancedSonnet 5$3.00$15.00The default. Synthesis, drafting, code changes, most day-to-day work
deepOpus 5$15.00$75.00Design reasoning, adversarial review, marking other models' work

Deep costs fifteen times what fast does on the way in, and fifteen times on the way out. Today's job is a code change with a written specification in front of it and a test suite behind it. That is drafting against a fixed target, which is the balanced tier's description word for word. Set it:

claude code 
/model sonnet
Expected. One confirmation line:
output
Set model to Sonnet 5 and saved as your default for new sessions
If you were already on Sonnet, nothing changes. The wording varies a little between Claude Code versions; the tier is the part that matters.
When not to use AI at all. Three questions get asked in this lab, and no model gets a vote in any of them:
  • Did the tests pass? pytest already answered. Its answer is not an opinion and cannot be improved by a second one.
  • Is the lint clean? ruff already answered, against a ruleset pinned in ruff.toml so that everybody sees the same findings.
  • Do the field names match on both sides of the boundary? A contract test answers, by failing.
Asking a model to confirm any of the three is redundant verification, the fifth row of templates/anti-pattern-checklist.md: paying for a second and less reliable answer to a question that is already settled. This week's hands-on audits a real workflow against all six rows of that list.
3The Python side 12-22 min

Why. One concern, one small diff. A change you can read in a minute is a change you can gate; a hundred-line diff gets waved through.

a. Paste this into Claude Code. It is long because it is specific, not because it is polite:

4The Java side 22-30 min

Why. Half a contract is worse than none. If only Python changes, Billing keeps returning the old total, OrderCore quietly falls back to its own calculation, and the invoice looks fine while being wrong by the discount.

a. The other half:

prompt 
Implement the Billing half of HEL-207.

apps/billing/src/main/java/com/helios/billing/InvoiceCalculator.java
- Add MAX_DISCOUNT_PERCENT = 50 beside TAX_RATE_PERCENT.
- Invoice gains a discountPence field, set in the constructor and written by
  toJson between subtotalPence and taxPence.
- calculate takes a fourth argument, discountPercent. Reject below 0 or above
  MAX_DISCOUNT_PERCENT with IllegalArgumentException. Work out
  discount = roundHalfUp(subtotal * discountPercent, 100), take it off the
  subtotal, and charge tax on what is left.

  a discount of 0, so the current callers and tests still compile.

apps/billing/src/main/java/com/helios/billing/BillingServer.java
- invoiceFromRequest reads an optional discountPercent, defaulting to 0, and
  passes it to calculate.

apps/billing/src/test/java/com/helios/billing/BillingServerTest.java
- Add two cases: appliesTheDiscountBeforeTax and aDiscountAboveFiftyIsRejected.
  The first sends 100 units at 189 pence with discountPercent 10 and expects
  discountPence 1890, taxPence 3402 and totalPence 20412 - the same figures the
  Python test uses.

No new runtime dependency in Billing. When you have finished, compile the main
sources with javac and tell me whether it built. Then write

agree on. Reply with one line: whether it compiled.

You chose the smaller diff over the louder failure. Put that sentence in week3/change-java.md - your rubric asks for it in step 6.

5The two gates that are not opinions 30-34 min

Why. Everything after this step is judgement. These two commands are the only answers today that do not depend on anybody agreeing with them.

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
python -m pytest apps/ordercore/tests
python -m ruff check apps/ordercore
Expected. Fifteen dots, then two lines:
output - the counts are exact, the timing is yours
...............                                                          [100%]
15 passed in 6.41s
All checks passed!
Fifteen, not eleven. Eleven tests were already there and four are yours. A count of eleven means Claude wrote no tests; twelve or thirteen means it wrote fewer than the four you asked for. The seconds are yours and vary run to run.
A failing test is information, not a setback. Read the assertion line before you do anything else. tax_pence coming back as 3780 rather than 3402 means the discount was worked out and then not taken off before tax - which is acceptance criterion three, caught by the gate that exists for it.
What these two gates do not cover, said plainly. Two things, and the second is the one that matters.
  • The Java tests are JUnit and run under Maven, which is not installed on the workstation. BillingServerTest.java is written today and not run today. What was executed on the Java side is the compile in step 4.
  • Nothing at all tests what actually crosses the wire. The Java test builds its own request string, so it never sees what billing_client.py sends. All four of your Python tests reach the fallback, which works the discount out locally, so none of them sees what Billing replies. Both sides are tested. The sentence between them is not.
That second gap is a fact about your change, not a mood. Write both into your rubric's evidence column in the next step rather than pretending them away, and expect the contract row to cost you a point. A gate that lies about its own coverage is worse than no gate. The challenge at the end of this book shows you the gap live, in about a minute.

b. Three edits, by hand, in that tab. This is the typing you came here to do:

  1. Retitle it for HEL-207, so it reads as a gate for this change rather than as a general document.
  2. Add a sixth criterion for what this ticket is actually about: the discount range. Score 0 if the range is enforced on neither side, 1 if on one, 2 if on both with a test that names the boundary. Raise the threshold to 10 of 12 and keep the rule that no criterion may sit at 0.

Challenge - break the contract on purpose

5 minutes, afterwards

Ask Claude to remove discountPercent from the outgoing payload in billing_client.py and change nothing else, then run the tests again. Put it back afterwards with git checkout -- apps/ordercore/app/billing_client.py.

All fifteen still pass. That is the result, and it is the uncomfortable one. Every test that reaches the client takes the fallback, which works the discount out locally from the order it already has, so none of them notices that Billing was told nothing. The Java test does not notice either: it builds its own request string and never sees what Python sent. A live Billing service would return a total with no discount in it, and the Shop would show that total.

Two things would have caught it, and neither is in your change. request_invoice takes a client argument precisely so a test can stand one in and assert on the payload it was handed. Or an end-to-end run with Billing actually started. Pick one, add it, and watch the contract row of your rubric move. Then write the general version down somewhere your team will read it: a green suite is evidence about what it covers, and no evidence at all about what it does not.

Passing bar

An impact note naming seven files to change and at least one place the entity map is wrong. The change made across Python and Java in two diffs you read. Fifteen tests passing and the linter clean, both run by you rather than reported to you by a model. A gate rubric with six criteria and an evidence column you filled in before scoring. A score you gave yourself against it. One rework item done, or a written reason there were none. One local commit holding the code and the evidence together.
