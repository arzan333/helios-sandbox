Mindset and AI-Native Workflow Design

Self-paced. Work through it in order. Every command has a copy button.

Time 45 minutes You produce week1/blueprint.md Committed locally, never pushed Needs Claude Code, Python, this repository
Before you start. You should already have run Setup-HeliosWorkstation.ps1, cloned this repository, created your own branch, and filled in templates/baseline-capture.md. If any of those are outstanding, do them first — this lab assumes them.

What this lab is really about

You already use Claude Code. The gap this week is method, not access. So the lab does not teach you to prompt. It asks you to look at a process that is genuinely slow, find out why from data rather than opinion, and decide where a human must sign before work continues.

You will finish with a workflow blueprint. It is the input to Week 3, so it is worth doing properly rather than quickly.

1Find the waits 0–8 min

Start your working copy and get the numbers. Run this from the repository root:

powershell 
python apps/insight/report.py stages --workflow intake
Expected. A table of eleven stage transitions with a median and a p90 column, then the three longest by median, then your end-to-end median, rework rate and the top rework reasons. It needs nothing installed beyond Python. Keep this output open — you will check Claude's answers against it later in the lab.

Now use Claude Code to interpret it rather than to fetch it. Open Claude Code in the repository and give it this:

prompt 
Read data/helios-tickets.csv and docs/process/requirement-intake.md.
For the intake workflow only, tell me the three longest stage transitions by
median duration. For each one, say whether it is a queue (the ticket is waiting
for a person or an environment) or effort (someone is actively working).
Cite the step number from the narrative. Answer in a table, nothing else.
Watch for. The third longest is not a queue. If Claude tells you all three are waits, it has pattern-matched instead of reading. Push back and make it justify each one against the narrative.

Record the table in section 1 of your canvas.

2Classify every step 8–16 min

Copy templates/blueprint-canvas.md into your own week 1 folder first, so the template stays clean for everyone else:

powershell 
mkdir week1 -Force
if (-not (Test-Path week1\blueprint.md)) { copy templates\blueprint-canvas.md week1\blueprint.md }

Now go through the narrative and classify each step as AI-ready, AI-assisted or human-only. Write your own one-line justification for each. Then have Claude Code challenge you, not do it for you:

prompt 
Here is my classification of the intake steps. For each row, argue the opposite
case in one sentence. Where my justification is really just "it would be faster",
say so plainly. Do not rewrite my table.
A step is AI-ready when the scope is bounded, the output can be verified, and being wrong is reversible. If any of those three is missing, it is not AI-ready no matter how repetitive it looks.
3Redraw the target state 16–26 min

Pick one pattern and commit to it:

PatternFits
Draft-Review-ApproveRequirements, specs, documentation, release notes
Analyze-Validate-EscalateDefect triage, incident response, impact analysis
Generate-Verify-PublishCode, tests, configuration

In section 3 of your canvas, state what disappears, what merges and what is untouched. Being explicit about what you are not changing is half the value.

Anti-pattern. Putting AI at the approval step. AI drafts and analyses; a named human approves. If your target state has a machine approving something, redraw it.
4Place your gates 26–36 min

A gate is a point where work stops until a named person signs. Minimum two. Fill in section 4 of the canvas. Owner roles must come from the RACI in docs/helios-landscape.md — Business Analyst, Developer, Architect, Quality Engineer or Release Manager.

Now look at a real design document that went through the existing review, docs/design/HEL-142-hld.md:

powershell 
type docs\design\HEL-142-hld.md

Read it and decide, on your own judgement, whether it should pass a design gate. Write your verdict and one sentence of reasoning at the bottom of your blueprint.

Compare with the person next to you. You will probably disagree, and you will both be able to defend your answer. That disagreement is the reason Week 3 introduces a rubric. Do not resolve it now.
What the architect actually left out (open only after you have decided)

No out-of-scope statement. Insight reads order data and is never mentioned. The spreadsheet import has no owner and no home. "About three days" has no basis. The one-line risk has no response and no owner. No alternative was considered. The review_date in the front matter is unset.

None of that makes it obviously a fail. That is the point.

5Baseline the metrics 36–43 min

Get your rework rate and cycle time from the data, not from the narrative:

prompt 
From data/helios-tickets.csv, for the intake workflow only, calculate:
1. median working hours from created to closed
2. percentage of tickets with rework_count above zero
3. the three most common rework_reason values with counts
Show the numbers only. Then tell me which of the three is most likely caused by
the gate I am adding, and why.

Put those numbers in section 5 and set a target next to each. A target without a number is a wish.

6Self-check and commit 43–45 min

Run the eight-point check in templates/self-check-8.md. Fix anything that fails. Then:

powershell 
git add week1/blueprint.md
git commit -m "Week 1: workflow blueprint for intake"
Local only. Do not push. Nothing in this programme leaves your machine.

Passing bar

Every insertion point has a gate. Every gate names a single role and says what happens when the check fails. Every metric in section 5 has a number that came from the CSV. If a facilitator asks "where did this number come from", you can show them the command.
