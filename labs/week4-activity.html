Helios Week 4 hands-on Training environment

Package a Skill, and Finish the Repository

On your own. 45 minutes. Nothing here depends on the lab, and step 0 fetches and rebuilds everything you need. Every command has a copy button.

Time 45 minutes You produce a technical specification with its tables back, front matter on every file, a long document split at its own section boundaries, a CLAUDE.md under 400 words, a Skill that triggers without being named, one Week 2 prompt scored twice, and a governance check Committed locally, never pushed Needs Claude Code 2.1.211 or later, Python 3.11, pandoc, markitdown with its PDF extra, VS Code, this repository
What you are finishing. Two OrderCore specifications have been converted out of Word and PDF into markdown. The conversion carried the words and broke the tables, gave nothing an owner, and left a five-thousand-word document in one file. None of that is retrievable yet. You finish it, and then you package the one piece of judgement you have that a repository cannot hold - a repeatable job - as a Skill.

The claim on trial. That a Skill nobody has to remember to invoke is worth more than a prompt somebody has to find. You test it the only way that counts: by asking a question that never mentions it, and seeing whether it fires.
Did you miss the lab? Nothing below needs it. Step 0 converts both documents and repairs their headings if that has not already happened, so it starts from the same place either way. If you did the lab, step 0 finds the files and creates nothing.

1Put the tables back 0-7 min

Why. A table is how a specification says "these things vary together". Broken into prose it becomes a paragraph nobody can diff, and a row that goes missing goes missing silently.

a. Look at the damage first, so you know what to check afterwards:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\repo\specs\ordercore-techspec.md
python -c "import re,pathlib; t=pathlib.Path('week4/repo/specs/ordercore-techspec.md').read_text(encoding='utf-8'); print(len(re.findall('(?m)^[|][-| :]+[|]', t)), 'separator rows'); print(len(re.findall('(?m)^[|]', t)), 'lines that start as a table row')"
Expected. A listing, then two counts that do not add up:
output - exact
9 separator rows
17 lines that start as a table row
The document has four tables with nineteen data rows between them: the field mapping in 2.1, the configuration table in 5, the testing table in 6 and the known gaps table in 7. Nine separators for four tables means the converter started a fresh table every time a row wrapped onto two lines in the PDF.

Break the seventeen down and it is worse than it looks: four headers, nine separators and four surviving data rows - order_id, subtotal_pence, Lint and TG-2. A repaired file would have four headers, four separators and nineteen data rows, which is twenty-seven lines. Fifteen of the nineteen rows are sitting in the file as plain prose.

One of those nine "separators" is not a separator at all. It is the second half of a testing row that wrapped in the PDF, whose first cell came out empty, so it reads as pipes, spaces and dashes - and the check's regular expression cannot tell that from a rule. The measurement is right and its label is not, which is the sort of thing worth catching now rather than after you have quoted it.

They are not lost. Every word is still there, immediately above or below the header it belongs to. Putting them back is mechanical, which is why the next part is a prompt and not an afternoon.

Six field mappings, five configuration settings, three test suites, five known gaps - nineteen rows. A count higher than that is an invented row, and the usual one is a sixth known gap, because five is an odd number of gaps to have. Ask it to quote the line each row came from.

2Front matter on every file 7-14 min

Why. A file with no front matter is a file nobody owns, and an unowned document does not go stale - it just becomes wrong while everybody keeps trusting it.

The schema is templates/frontmatter-schema.md: four required fields, owner, version, effective_date and review_date, plus source on anything converted and an optional status. Two of them do the work. owner is one role, never a team, because a team cannot answer a question. review_date is the only field that makes staleness visible at all.

a. Add it everywhere it can be derived, and flag where it cannot:

templates/frontmatter-schema.md exactly: the block is the first thing in the
file, nothing above it, ISO dates, the four required fields in the schema's
order.

not a document in the repository, and it has no owner separate from the
repository itself.

Where a file was converted from an original, take owner, version,
effective_date and review_date from that original's row in
docs/governance-log.md, and add source: naming the original. Do not invent a
date that is in that file.

Where a file is new today - an index, the gap register - there is no row to

review_date field. Set version 1.0 and today's date as effective_date. Leave
both placeholders exactly as written; I fill them in.

Why. Retrieval works on whole files. A five-thousand-word file answers a question about tax by handing over everything anybody ever wrote about orders, and you pay for all of it on every request.

a. Find out which files are too big. The rule of thumb is about 1500 words:

5Build a Skill, and make it fire 27-35 min

Why. A prompt is something somebody has to find and paste. A Skill is the same knowledge attached to the words people already use, so it arrives without anybody remembering it exists. Whether it fires is a property of one sentence, and that sentence is the whole exercise.

a. Read the worked example first. It is deliberately small:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir skills\example-skill\SKILL.md
type skills\example-skill\SKILL.md
Expected. A listing, then a short file. These two lines are the whole of the trigger:
output - skills/example-skill/SKILL.md, the front matter
name: stage-report
description: Summarise Helios delivery stage durations from data/helios-tickets.csv. Use when asked about cycle time, stage waits, bottlenecks, rework rates, or how long a Helios workflow takes.
Look at what that description does and does not do. It says what the job is in one clause, and then it lists the words somebody would actually type - "cycle time", "bottlenecks", "how long a workflow takes". It never says "use this skill when you need the stage report skill", which is the most common way a description fails: it triggers only on its own name, and somebody who knew the name did not need it.

The body is equally deliberate. One job, the command to run, how to read the answer, and three rules - including "if asked about a workflow that is not in the list, say so rather than guessing". The detail that would have doubled its length is left in docs/process/ and pointed at.

b. Build yours. One job, one page, and a description written for a stranger:

prompt - coding 
Read skills/example-skill/SKILL.md and use it as the pattern.

Write week4/skills/ticket-impact/SKILL.md - a Skill that turns a Helios
ticket key into an impact note. That is where you author it; the next step
installs it where Claude Code looks.

Front matter: name, then description. The name must be exactly
ticket-impact, matching the folder it sits in - a name that disagrees with its
folder is the other common reason a hand-written Skill never loads. The
description says what the job is in
one clause and then names the words somebody would actually type when they
want it - which files a change touches, what a ticket affects, what breaks if
I change this, who has to approve it. It must not mention the skill's own
name, and it must not say "impact note" only, because nobody asks for one by
that name.

Body, under a page:
- Where to look: helios-backlog/<KEY>.json for the ticket, data/entity-map.md
  for what each concept touches, and the files the map names.
- What to produce: a table of File, Change needed, Why; a section for anything
  that must change and is not in the map; a section for acceptance criteria
  that are out of scope.
- Rules: decide from the code, not from the map, because the map says of
