Helios Week 4 hands-on Training environment

Own It, Split It, Package It

On your own. 40 minutes. Nothing here needs the lab - step 0 builds whatever is missing. Every command has a copy button.

Time 40 minutes You produce an owner and a review date on every file, a five-thousand-word specification split at its own section boundaries and indexed, and a Skill that fires on a question that never names it Committed locally, never pushed Needs Claude Code 2.1.211 or later, Python 3.11, pandoc, markitdown with its PDF extra, this repository
What you are finishing. Two specifications for an order service have been converted out of Word and PDF into markdown with real headings and whole tables. They are readable. They are not yet retrievable: nobody owns them, nothing says when they go out of date, and one of them is five thousand words in a single file. You fix all three, and then package the one thing a repository cannot hold - a repeatable job - as a Skill.

The claim on trial. That a Skill nobody has to remember to invoke is worth more than a prompt somebody has to find. You test it the only way that counts: by asking a question that never mentions it, and watching whether it fires.

The shape of the session

StepWhat you doTime

2Split the long one at its own section boundaries, and index it8-18

Three prompt patterns, and every prompt below is labelled with one in the grey bar above its copy button. analysis reads and reports, and always names its evidence. coding transforms files, and is always followed by a command that checks it. validation checks a claim somebody has already made, and never writes the thing it is checking. Labelling costs no time; a prompt that does two of the three has marked its own homework.

Why. Four minutes now, or a confusing error in six, and this also builds anything the lab would have left behind.

1An owner and a review date on every file 0-8 min

Why. A file nobody owns does not go stale so much as quietly become wrong, and a review date is the only thing that makes that visible from outside.

a. One coding prompt covers every file at once:

prompt - coding 
Give every markdown file under week4/repo a front matter block, following
templates/frontmatter-schema.md exactly: the block is the first thing in the
file with nothing above it, ISO dates, the four required fields in the
schema's order. Where a file already has a block that follows the schema,
leave that file alone.

Skip week4/repo/CLAUDE.md if it is there. It is instructions to a tool, not a
document about the service, and it has no owner separate from the repository
itself.

A converted specification takes owner, version, effective_date and review_date
from the row for its original in docs/governance-log.md, and gains a source
field naming that original. Invent no date.

An index file was written today and has no row to copy, so it takes owner
Architect, version 1.0, effective_date today, and review_date six months after
today. week4/repo/index.md is one of these.

Find the files rather than assuming which ones exist. Change nothing below the
front matter block in any file, and do not edit docs/governance-log.md. Reply
with one line: how many files now have front matter, and how many you added.
Expected. Four files covered, and a count of what was added:
output - if you did the lab; it reads 4 added if you came straight here
4 files have front matter, 0 added
The two specifications take their owner and dates from a row that already exists. The two index files were written today and have no row to copy from, so the book supplies the rule instead: the Architect owns an index, and six months is long enough for a file that only points at other files. There is no source for an owner except somebody deciding, and deciding once for everybody is what keeps forty people from inventing forty different answers.

b. Check every file, not the two you happen to remember:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\repo
python -c "import datetime,pathlib; g=lambda t,f: next((l.split(':',1)[1].strip() for l in t.splitlines() if l.startswith(f)), 'MISSING'); today=datetime.date.today().isoformat(); [print(('ok  ' if t.startswith('---') and 'MISSING' not in (g(t,'owner')+g(t,'review_date')) else 'FIX '), g(t,'owner'), g(t,'review_date'), 'past' if g(t,'review_date') < today else 'current', p.as_posix()) for p in sorted(pathlib.Path('week4/repo').rglob('*.md'), key=lambda q: q.as_posix()) if p.name != 'CLAUDE.md' for t in [p.read_text(encoding='utf-8')]]"
Expected. A listing of what is in the repository, then one line per document, all of them ok:
output - the two 2027 dates are six months from the day the indexes were written
ok   Architect 2027-03-18 current week4/repo/index.md
ok   Architect 2027-03-18 current week4/repo/specs/index.md
ok   Product Manager 2026-07-12 past week4/repo/specs/ordercore-fsd.md
ok   Architect 2026-09-03 past week4/repo/specs/ordercore-techspec.md
A FIX means one of two things: the block is not the first thing in the file, or a required field is missing. From a tool's point of view those are the same failure - a file it cannot place - so the check does not distinguish them.

Two past is the point of the step. Nothing happened to those two specifications this morning; a date that had already gone by is now in a field a command can read, instead of being invisible inside a document nobody re-opens. That is all a review date does, and it is enough to make a stale document announce itself.
2Split the long one, and index it 8-18 min

Why. Retrieval works on whole files, so a five-thousand-word file answers a question about tax by handing over everything anybody ever wrote about orders.

a. Find out which file is too big. The rule of thumb is about 1500 words:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
python -c "import pathlib; [print('%6d  %s' % (len(t.split()), p.as_posix())) for p in sorted(pathlib.Path('week4/repo').rglob('*.md'), key=lambda q: q.as_posix()) if p.name != 'CLAUDE.md' for t in [p.read_text(encoding='utf-8')]]"
Expected. One line per file, and one of them an order of magnitude bigger than the rest:
output - your counts will be close to these, not identical
    54  week4/repo/index.md
    62  week4/repo/specs/index.md
  5071  week4/repo/specs/ordercore-fsd.md
   793  week4/repo/specs/ordercore-techspec.md
Exactly one file is over the line and nothing else is close. The functional specification is about three and a half times the limit. The technical one is a fifth of it and stays whole, because splitting a file that does not need splitting adds a layer of indirection for nothing - 1500 is a threshold, not a target.

b. Split it at its own boundaries, never at a word count. A coding prompt:

prompt - coding 
Split week4/repo/specs/ordercore-fsd.md into parts under
week4/repo/specs/ordercore-fsd/.

- Split only at level-2 headings, which are the document's own numbered
  sections and its appendices. Never split inside a section, never split
  inside a table, and never split to hit a word count.
- Where consecutive sections are short, put them in one part. Where a single
  section is over about 1500 words on its own, leave it over and say so in the
  reply: a section is the smallest honest unit.
- Name each part NN-slug.md, numbered in document order, the slug taken from
  the heading.
- Every part carries the same front matter as the file it came from, plus
  part: N of M, plus covers: listing the section numbers in it.
- Write week4/repo/specs/ordercore-fsd/index.md, with the same front matter as
  the other index files: one row per part - file, section numbers, and one
  clause on what is in it. No summaries of content.
- Then delete week4/repo/specs/ordercore-fsd.md and update both
  week4/repo/specs/index.md and week4/repo/index.md, so that nothing anywhere
  points at a file that no longer exists.

Move text, do not rewrite it. The parts joined back together must be the same
document. Reply with one line: how many parts, and the largest part's word
count.
Expected. Somewhere between six and ten parts, none of them very large:
output - the number of parts varies; the second figure should land near 960
8 parts, largest 982 words
Six to ten parts all describe the same document; it depends only on how hard short sections were grouped. The second number is the one to check. The longest single section in the document is about 960 words, so a largest part much above that is two sections that should have been two parts, and a largest part over 2000 means sections were concatenated rather than grouped and the split did nothing.

c. Prove nothing was lost in the splitting. This is the check that matters:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\repo\specs\ordercore-fsd
python -c "import re,pathlib; ps=sorted(pathlib.Path('week4/repo/specs/ordercore-fsd').glob('[0-9]*.md')); b=[re.sub('(?s)^---.*?---','',p.read_text(encoding='utf-8')) for p in ps]; print(len(ps), 'parts'); print(sum(len(x.split()) for x in b), 'words in the parts'); print(sum(len(re.findall('(?m)^[|][-| :]+[|]', x)) for x in b), 'tables in the parts'); print(max((len(x.split()) for x in b), default=0), 'words in the largest')"
Expected. A listing of the parts, then four numbers. The middle two are the ones to read:
output - the word counts are yours, the table count is not
8 parts
5056 words in the parts
6 tables in the parts
962 words in the largest
Six tables. That is the number the functional specification started with and the number that has to come out the other side. Five means a table was split across two parts and one half lost its header. Seven means one got cut in two and both halves grew a separator of their own.

The word total should land within a hundred or so of the figure you saw in part a. This check strips each front matter block before counting, which is why the largest part reads a few words lower here than in the reply to part b. A drop of several hundred means a section was summarised rather than moved, and that is the failure to send back: the parts joined together have to be the same document.
3Package a repeatable job as a Skill 18-27 min

Why. A prompt is something somebody has to find and paste, and a Skill is the same knowledge attached to the words people already use.

a. Read the worked example first. It is deliberately small:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir skills\example-skill\SKILL.md
type skills\example-skill\SKILL.md
Expected. A listing, then a short file. These two lines are the whole of the trigger:
output - the front matter of the worked example
name: stage-report
description: Summarise Helios delivery stage durations from data/helios-tickets.csv. Use when asked about cycle time, stage waits, bottlenecks, rework rates, or how long a Helios workflow takes.
Look at what that description does. It says what the job is in one clause, and then it lists the words somebody would actually type - cycle time, bottlenecks, how long a workflow takes. It never says "use this when you want the stage report skill", which is the commonest way a description fails: it then triggers only on its own name, and somebody who knew the name did not need it.

The body is equally deliberate. One job, the command to run, how to read the answer, and three rules. The detail that would have doubled its length is left in another file and pointed at.

b. Write yours. One job, one page, and a description written for a stranger:

prompt - coding 
Read skills/example-skill/SKILL.md and use it as the pattern.

Write week4/skills/doc-intake/SKILL.md - a Skill that prepares a new document
for this repository. That is where you author it; the next block installs it
where Claude Code looks for it.

Front matter, two fields:
- name: exactly doc-intake, matching the folder it sits in. A name that
  disagrees with its folder is the other common reason a hand-written Skill
  never loads.
- description: one clause saying what the job is, then the words somebody
  would actually type when they want it. It must contain all five of these
  words - document, owner, review, repository, add - and it must not contain
  the word skill, and it must not mention its own name.

Body, under a page:
- What to produce: a front matter block following templates/frontmatter-schema.md,
  and the row to add to week4/repo/specs/index.md.
- How to fill it: owner is one role and never a team; effective_date is today;
  review_date is six months after effective_date for anything that only points
  at other documents, and the date carried over from the original for anything
  converted; a converted document keeps a source field.
- Rules: never invent an owner or a date - say which one is missing and who has
  to decide it. Never write a review date more than twelve months out. Say
  plainly when a document is too long to go in whole.

Then write week4/skill-notes.md: the description you used, and the five or six
phrases you expect it to fire on.

Reply with one line: the description, exactly as you wrote it.
Expected. Two files, and the description read back to you:
output - yours will differ, the shape should not
Prepare a document for this repository: its front matter, its owner and its review date, and the index row to add. Use when asked how to add a document, who should own a file, when something must be reviewed again, or where a new file goes.
One clause of job, one clause of trigger words. A description that reads "use this when you want a document intake" will only fire for somebody who already knows it is there, which is the one person who does not need it.

c. Install it where Claude Code looks, then restart - Skills are discovered when a session starts:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\skills\doc-intake\SKILL.md
if (-not (Test-Path .claude\skills\doc-intake)) { mkdir .claude\skills\doc-intake -Force | Out-Null }
copy week4\skills\doc-intake\SKILL.md .claude\skills\doc-intake\SKILL.md
python -c "import pathlib; p=pathlib.Path('.claude/skills/doc-intake/SKILL.md'); print('installed' if p.exists() else 'MISSING', p.as_posix())"
claude
Expected. One listing, one confirmation line, then a fresh Claude Code session:
output
installed .claude/skills/doc-intake/SKILL.md
You author it in your own folder and install it somewhere else. Claude Code discovers project Skills in .claude/skills/ at the root of the repository it was started in, so a SKILL.md sitting in your week folder is a markdown file nobody reads. Keeping the authored copy under week4 is what makes it your work rather than a change to the repository's configuration, and step 5 commits both.

Run this in your PowerShell window. Its last line starts a fresh Claude Code session there, and that is the session step 4a uses. Your original Claude Code window was started before the Skill existed and is now out of date: type /exit in it, and use it for the two PowerShell blocks that are left.

A session that was already running when the file was installed does not know it exists, which is the commonest reason a Skill looks as though it did not trigger. The restart is what rules that out.
4Make it fire without naming it 27-36 min

Why. Whether a Skill is worth having is decided by one sentence of description, and the only honest test is a question that never mentions it.

a. Paste this into the session step 3c just started. It is an analysis prompt, and it never names the Skill:

prompt - analysis 
I have just written a short design note about delivery windows and I want it
to sit alongside the two specifications. What does it need before it can go
in, and who should it belong to?

Write the answer to week4/skill-test.md.
Expected. The session names your Skill before it answers:
output - what you are looking for in the transcript
Skill: doc-intake
The exact wording of that line moves between Claude Code versions - it may sit on its own line, or in the list of what the session is about to do. What you are looking for is the name doc-intake appearing at all, before the answer.

Read the answer as well as the transcript. There is no such note in the repository, so the answer is a recipe rather than a filled-in block - a good one says that plainly, lists the front matter fields the note would need, and names the role that has to decide the owner rather than picking one itself. Those are the Skill's own rules. A Skill that fired and then ignored them is a failure of the body, not of the description, and it is a different fix.

b. Now see why it fired. The trigger is not magic and it is not the name:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\skill-test.md
python -c "import pathlib; d=next((l for l in pathlib.Path('.claude/skills/doc-intake/SKILL.md').read_text(encoding='utf-8').splitlines() if l.startswith('description:')), '').lower(); [print(('carried  ' if w in d else 'MISSING  '), w) for w in ['document','owner','review','repository','add']]"
Expected. A listing, then five lines the same:
output
carried   document
carried   owner
carried   review
carried   repository
carried   add
That is the whole mechanism. Nothing below the description is read until the Skill has been chosen, so the description is the only part of the file doing that work. The question in part a never said doc-intake, and it never said "front matter" either - it said "go in", "belong to" and "alongside the two specifications". The description carried the vocabulary of the job - document, owner, review, repository, add - and that was close enough to what was being asked. A description that only described itself would not have been.

A MISSING line means the description dropped a word the step 3b prompt required. Send that prompt again, run step 3c again so the installed copy is the new one, and repeat part a in a fresh session.

If the transcript in part a never named the Skill, that is a finding, not a setback, and it is worth writing one line about in week4\skill-notes.md: a description that does not fire is the most common way a Skill quietly costs more than it saves.
5Commit 36-40 min

Why. The Skill is the only thing you made today that lives outside your own folder, so it has to go into the commit deliberately.

a. Everything as one thing:

powershell 
cd $env:USERPROFILE\Helios\helios-sandbox
dir week4\skill-notes.md
git add week4 .claude
git commit -m "Week 4 hands-on: owners, review dates, a split specification and a Skill"
git log --oneline -1
Expected. One listing, then one commit:
output - the hash and the branch name are yours
skill-notes.md
[main b7e4d10] Week 4 hands-on: owners, review dates, a split specification and a Skill
b7e4d10 Week 4 hands-on: owners, review dates, a split specification and a Skill
Git lists every file it added and removed between those two lines; the commit line and the log line are the two to read, and the eight parts of the split specification are why the list is long. .claude is in that commit on purpose: it is where the Skill has to live to be found. Nothing is pushed; a hook blocks it.

Take it back to your desk

15 minutes, optional

Everything above worked on documents about a company that does not exist. The version that pays is the one you run on a document your team actually argues about, and it is the same four moves:

MinutesDo this
0-4Take the one document your team quotes most often and cannot search. Convert it - pandoc for Word, markitdown for PDF - and count the headings you got
4-8List its figures. For each, ask whether the fact in the picture is anywhere in the text. That list is the deliverable, more than the conversion is
8-12Give it front matter. The two fields that matter are the two nobody can derive: who answers when it is wrong, and how long it may be wrong for
12-15Write the description line for a Skill that does the job you did twice this week. If you cannot name the words somebody else would type, it is not a Skill yet

Passing bar

Front matter first thing in every markdown file under week4\repo, with an owner and a review date on each, and the two converted specifications reading past. The functional specification split at its own section boundaries, no part much over 1500 words, all six of its tables still present, and an index that points rather than summarises. A Skill in .claude\skills\ whose description carries all five required words, tested with a question that never named it, and the result written down whichever way it went. One local commit holding week4 and .claude together.
